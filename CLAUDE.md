# aello

Isolated Claude Code environments — like Python venvs, but for AI agents. Claude-only, subscription-auth, cross-platform (Linux + Windows x86_64; macOS from source).

## Docs — keep in sync with code changes

- `README.md` — user-facing: install, concepts, quick start, command + role reference. Update when commands or roles change.
- `CHANGELOG.md` — version history of user-facing changes. Every user-facing change gets an entry, in the same commit as the code.
- `docs/` — deeper reference, in `docs.rs::ORDER` reading order: `concepts.md` (isolation model, auth, contextdb), `roles.md` (role → scaffold/`/sync` mapping, the pre-0.2 capability migration, git attribution), `workflows.md` (task-shaped walkthroughs: first env, two agents in one repo, the session loop, rename, purge — the page to extend when a new usage pattern appears), `skills.md` (the four seeded skills in detail, manual-only enforcement, `.aello-keep`), `voice.md` (the whole TTS path: vendoring, the five files, toast identity, `HOOK_VERSION`, troubleshooting), `upgrading.md` (the page to point an env at the first time it meets 0.2 — roles migration, removed flags, the pre-0.2-binary hazard), `migrate.md` (migrating an existing repo onto aello: validated flow + gotchas), `development.md` (building aello itself: verification rule, re-vendoring, release process, commits), `troubleshooting.md` (failure modes and what they actually mean). **`docs/` is for developers and `README.md` is for users** — if a README section only makes sense to someone who has read the source, it belongs here instead. **`docs/` is also the in-app help**: it's embedded into the binary (`docs.rs`) and rendered by `aello docs` (CLI) and the TUI reader (`?`), so `docs/` is the single source of truth — add a `.md` and it appears with no code change. Keep these in sync with behavior.
- This file (`CLAUDE.md`) — agent/architecture notes. Maintain as the design evolves.
- `site/` — the landing page. A **static Next.js** app, entirely separate from the Rust crate: `cargo build`/`cargo test` never touch it, and it ships nothing into the binary. Its design tokens are transcribed verbatim from a captured GitHub design system into the `:root` block of `site/app/globals.css` — change values there, never inline in a component. `npm run build` in `site/` emits plain HTML in `site/out/`. See `site/README.md`; update the page when the install steps, command list, or role table change. **`/docs` on the site is generated from this repo's `docs/` at build time** (`site/lib/docs.ts`), the same files `docs.rs` embeds — one source, three readers (binary, TUI, web), so a new `.md` needs no site change either. `.github/workflows/pages.yml` deploys to GitHub Pages on any push to `main` touching `site/**` or `docs/**`, building with `NEXT_PUBLIC_BASE_PATH=/aello` (read by both `next.config.ts` and `lib/docs.ts`, unset locally). The landing page's Workflows section resolves its anchors from `docs/workflows.md`'s rendered headings and **throws at build time** if one is missing — a hardcoded anchor rots silently, which is the failure shape this repo keeps hitting.

## Architecture

**Blueprint** — a reusable agent identity in `config.toml`: `name`, `model`, optional `claude_md` (global persona), and a `role`. Reusable across projects.

**Persona lifecycle** — `claude_md` is one of three values, plus a legacy path. A coding project starts on **`coder`**; anything outside IT starts on **`none`** (blank, because a coding persona there is actively wrong); both become **`custom`** the first time a generated persona is accepted, after which `<env>/CLAUDE.md` is authoritative and `templates::resolve` returns `None` so `place` writes nothing over it. `sysadmin` was a fourth template and was **dropped** — barely used and effectively coder with different nouns. `Config::migrate_personas` (every load, idempotent, beside `migrate_roles`) folds absent → `none` and `sysadmin` → `custom`: the one env on it already holds that text, since personas are never clobbered, so `coder` would have been a false claim. **A path is still accepted** and deliberately not in the picker — five blueprints point at persona files the user maintains and three of them share one file, so collapsing those to `custom` would freeze the copies and end the sharing silently. Generation lives in **`<env>/persona.gen`** (`gen1 2026-08-03`), a sidecar rather than a config key or an `.aello.toml` field because both of those are rewritten from a struct on every `place` and would drop it — config answers *whether* an env has a custom persona, the sidecar answers *which generation*. `aello persona <name> --from <file> [--project <dir>]` (`cmd_persona`) does all three writes together; it is the **only** command that overwrites a persona, and it goes through aello because `Config` is serialized from its struct, so a key written into `config.toml` by anything else vanishes on the next save.

**Roles** (`models.rs::Role`) — one of `maintainer` / `contributor` / `standalone`, chosen at `add` time. `Role::caps()` expands it into the internal five-bool `Capabilities` struct that `project.rs` and `templates.rs` still work in, so a role is *only* a restriction on which combinations are offered — placement and `/sync` generation are unchanged. maintainer = all five; contributor = `github` + `changelog`; standalone = none. `Capabilities::any()` still gates seeding `/sync`. **Why three and not five checkboxes:** the flags were never independent per repo — one blueprint holds everything, the rest hold git duties only — and 32 of the 32 unused combinations were pure surface area. **Migration:** pre-0.2 configs carry `[blueprints.caps]`; `Config::migrate_roles` (called from `config::load`, every load, idempotent) folds it via `Role::from_caps` — prose caps (`project_md`/`docs`/`readme`) → maintainer, git-only → contributor, none → standalone — and `legacy_caps` is `skip_serializing`, so the old key disappears on the next save. Run on every load rather than behind a marker so a restored backup heals itself instead of silently loading as standalone. **`voice` was a sixth and is not any more** — every env speaks unconditionally, so there is no flag, no TUI row and no `--no-voice`; silence is `aello voice mute` at runtime. Serde ignores a leftover `voice = …` in an existing config and the next save drops it. `github` scaffolds the most: the `.claude-env-*` gitignore line, `.gitattributes` (CRLF normalize), a generic `VERSION` + stack-agnostic `.github/workflows/version.yml` patch-bump CI, and the tracked `claude-internal/` mirror (see below).

**`claude-internal/`** — a TRACKED folder at the project root, one-way mirror of the gitignored env dir, so a blueprint's skills/memory/persona reach git. **Namespaced per blueprint** (`claude-internal/<name>/...`) so multiple blueprints sharing one repo don't clobber each other's mirror. Three parts: `claude-internal/<name>/skills/` ← `<env>/skills/`, `claude-internal/<name>/memory/` ← `<env>/projects/<encoded-cwd>/memory/`, and `claude-internal/<name>/persona.CLAUDE.md` ← `<env>/CLAUDE.md` (renamed so Claude Code never auto-loads the snapshot). The live env dir stays the single source of truth; the mirror is written one-way from it (never read back). Seeded at placement (`scaffold_project` → `mirror_env_internal`, taking the blueprint name, github only, NOT added to the `.claude-env-*` gitignore) and refreshed + staged by the github `/sync` step, which self-heals the folder (`mkdir -p`) so already-placed envs adopt it.

**Env dir** — `<project>/.claude-env-<name>/`, the blueprint's `CLAUDE_CONFIG_DIR`. Holds `settings.json`, the global persona `CLAUDE.md`, `.aello.toml` (the placed Instance), `hooks/post-compact.py` + `hooks/session-end.py` + `hooks/session-start.py`, and the generated `skills/sync/SKILL.md`. Gitignored by convention (the `github` cap seeds the `.claude-env-*` ignore line).

**Two CLAUDE.md layers** — global persona (`<env>/CLAUDE.md`, set once, never clobbered) vs project (`<project>/CLAUDE.md`, maintainer only, maintained by `/sync`). Memory is separate: `place` seeds a starter working-style memory under `<env>/projects/<encoded-cwd>/memory/` on first placement (gated on `MEMORY.md` absence, never clobbered), then it's automatic (PostCompact hook).

**Auth** — `aello login` runs `claude setup-token`, stores a long-lived non-rotating `CLAUDE_CODE_OAUTH_TOKEN` in `config.toml`; every env exports it. Concurrency-safe across many parallel envs (the reason credential-copy was abandoned). On fresh envs, `mark_onboarded` seeds `hasCompletedOnboarding` so Claude skips its first-run wizard.

**contextdb** — three transcript hooks. **PostCompact** saves each compaction summary; **SessionEnd** captures a session ended without compacting (`/clear`/exit), archiving the `/handoff` note + transcript pointer to `<ts>_<session>_end.jsonl` and skipping subagent sessions. **SessionStart** is the consumer side: it delivers `<name>.HANDOFF.md` and `<name>.NOTE.md` into the new session as `additionalContext` and **deletes** them, which is what makes the `/handoff` and `/note` skills' "read on boot, then deleted" true and stops SessionEnd re-archiving the same stale note forever. It also emits a **standing block on every session** — "you are running under aello, named `<name>`" plus the four facts a session cannot otherwise learn: the env dir is gitignored and rewritten every run (`.aello-keep` to pin a skill), the seeded skills are the user's to type, other blueprints may share the working tree, and commits are attributed automatically. **Why the hook and not the persona:** a session had no reliable way to know aello existed — the env dir is gitignored, the persona is user-owned and usually silent, and a project `CLAUDE.md` only exists for a maintainer — so agents edited files the next launch overwrote and ran skills that are the user's alone. The persona is also the file most likely to be rewritten wholesale, while `place()` rewrites this script every run, so the block reaches an env placed months ago without touching anything the user owns. ~257 tokens per session; `session_start_hook_announces_the_aello_environment` pins the parts that carry the meaning, including that it is emitted even when no handoff or note is waiting (the early `sys.exit(0)` used to skip it). Existing envs self-heal both into `settings.json` on next `place` (`ensure_own_hook(settings, event, script)`, idempotent, never clobbers a user-edited file; an unparseable one warns on stderr and is left alone). Transcripts → `<contextdb>/<project>/<blueprint>/<ts>_<session>.jsonl`. Root in `config.toml` (`contextdb`, default `~/aello/contextdb`), passed as `AELLO_CONTEXTDB`. **SessionEnd does all the archiving in practice** — audited 2026-08-03: 265 SessionEnd records and **zero** PostCompact records for any aello blueprint, the newest compaction capture seven weeks old and from a pre-aello setup. PostCompact fires only on compaction and a 1M-context session ended with `/clear` never reaches it; it is dormant, not broken (the same script produced correct 7 KB/15 KB captures in June), so it stays seeded. **Every env launches with `--thinking-display summarized`** (`launch.rs::THINKING_DISPLAY`, appended before the user's `--` extras so one run can override it). The API default is `omitted`: thinking blocks arrive with an empty `thinking` field and only an opaque signature, which is what the transcript stored — measured 2026-08-03, 2,842 blocks across 53 transcripts, every one empty. `display` controls visibility only (thinking happens and is billed identically), so this is free; the raw chain of thought is never returned on any model and a summary is the ceiling. The flag is real but **undocumented in `claude --help`** — found by grepping the binary, and verified end-to-end by running a prompt through it and reading the captured summary out of the archived transcript. Unconditional for the same reason the voice is: it applies to every env and no blueprint has a reason to differ. **SessionEnd copies the transcript** to `<ts>_<session>_transcript.jsonl` rather than only recording its path, and notes the result in `transcript_archived`. The path alone was a reference that decayed: Claude Code deletes its own session files after `cleanupPeriodDays` (**default 30**) and the env dir is gitignored + `--purge`-able, so 15% of archives already dangled with a clean cliff at 30 days (6–14% dead under, 44% at 30–39) — silently, since nothing errors. `CLEANUP_PERIOD_DAYS = 365` now goes into `settings_json`, and `ensure_cleanup_period` self-heals it into existing envs **only when absent** so a user's own value stands. The copy streams (transcripts reach tens of MB) and opens the source before the destination, so a failed copy leaves no 0-byte file masquerading as an archive. It also prefixes both paths with `\?\` on Windows: the encoded-cwd directory repeats the whole project path, so a deep project pushes the transcript past the 260-char MAX_PATH and `open()` fails — measured at 325 chars, where the archive silently degraded back to a pointer and the `except` recorded that honestly, which is exactly how it stayed invisible.

**voice** (unconditional — every env) — a `Stop` hook that speaks each response's trailing `TL;DR:` line via Edge neural TTS, plus a `SessionEnd` group that releases the leased voice. Vendored from the `revoiced` project as **five** files copied together into `<env>/hooks/` (`hooks_speak.py` → `speak.py`, `hooks_duck.py` → `duck.py`, `hooks_focus.py` → `focus.py`, `hooks_notify.py` → `notify.py`, `hooks_win_audio.ps1` → `win_audio.ps1`): `speak.py` does `sys.path.insert(HERE)` + imports `duck`, `focus` and `notify` as siblings, and shells out to `HERE/win_audio.ps1`. **Vendor all five.** `duck` and `win_audio` are hard dependencies — without them a copy fails at runtime. `focus` and `notify` are imported **guarded** (`try`/`ImportError` → `SimpleNamespace` stubs), and that guard is exactly the trap: a three-file vendor still speaks, while `notify`'s stub returns `False` from `show()` and **no desktop notification is ever attempted, in any env, silently**. That is what happened on 2026-08-02 — notifications were off across the machine for two hours, reported broken twice and measured healthy twice (the tests ran the repo's copy, which has its siblings, not the env copy the hook executes). Guarded means "survives a partial copy", not "optional". Upstream `e95bd2b` made the fallback loud: a `MISSING` list rides on every history entry and `speak.py --status` leads with `INCOMPLETE COPY - no …`. **Drift check:** upstream keeps a module-level `HOOK_VERSION` in `speak.py`, bumped only when one of the five hook-path files changes; `project.rs` records the vendored value in `HOOK_VERSION` (currently **13**), two unit tests fail if a re-vendor moves one without the other, and `aello voice status` prints it. **13 added a Telegram sender** — the spoken line and its mp3 also go to a chat, opt-in behind `REVOICED_TELEGRAM=1` + `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID` (all three, or it is off) — and touched `speak.py` only, which is exactly the case the second test exists for in reverse: the other four were byte-identical and still get re-vendored, because "only one file moved" is how a partial vendor gets rationalised. Ask a *placed copy* what it is with `python <env>/hooks/speak.py --hook-version`, which prints before any optional import — so unlike `--status` it answers even from a partial copy. Two, because `HOOK_VERSION` lives in `speak.py` alone: the first compares the recorded constant to the vendored `speak.py`, the second digests **all five** files (CRLF-normalised, so a Windows checkout and Linux CI agree) so a re-vendor touching only `duck.py` or `win_audio.ps1` can't slip past. That second one first paid off on day one, catching the 3 → 4 bump, and again on the 4 → 5 that followed within the hour. **A stale copy is not merely out of date — it can damage the machine**, which is why a re-vendor is a rollout and not a version bump: at 8, `duck.py` deleted its record of the pre-duck volumes whenever it could not enumerate audio sessions (every poll off a second thread, since comtypes initialises COM per thread), so the next duck read the lowered volume as normal and squared it, and Windows keeps per-application volume in the registry against the executable path — it survives the process and the reboot. The fix is upstream at 11 — **10 was an incomplete fix and damages the machine too**: it kept the record but keyed it on the *pid*, and one process owns several audio sessions (`GetAllSessions()` yields one control per session, so a browser's media and notification streams collide), so the second reading overwrote the first while both were lowered and the restore raised one and dropped the other's record. Measured here after the 41-env backfill at 10: five applications at 0.15 from a single duck. 11 keys on `InstanceIdentifier`, still reads the pid-keyed records that copies on 10 left behind, and stops `restore()` running unlocked on a merely contended lock. Envs adopt a bump on their next `run`, and until then their copy is the thing doing it — which is why **a re-vendor is a rollout, and the sweep afterwards has to be the registry scan, not a live audio-session enumeration** (see `docs/troubleshooting.md`: the live check found 1 damaged application where the registry held 7, because Windows stores per-app volume per *endpoint* and the live API reads only the active one). A version, not a commit sha — revoiced's CI commits a `VERSION` bump on every push to main, so local shas get rewritten by the rebase and a recorded sha rots on its own. **Toast identity:** a Windows toast is shown *as* a registered AppUserModelID and one sent under an unregistered id is dropped with no error, so a machine that runs envs but never starts the revoiced station had notifications off everywhere — the same silent shape one layer out. `run_blueprint` calls `voice::ensure_notify_registered` after `place`, which runs the vendored `notify.py --register` unconditionally (best-effort; a missing `python` is not worth failing a launch over). Unconditional is safe **only since upstream `9d085c8`**, which split registration in two: the *identity* is a name any copy may claim, while the `revoiced:` *protocol* is a promise to run an `action.py` beside the copy that registered it — and an env's `hooks/` has none, since aello vendors the five hook-path files and not the station. Before the split, registering from an env repointed both toast buttons at a missing file, on exactly the machines a station had working; aello shipped a `reg query` guard for one release (v0.1.61) and dropped it once the default became correct. It lives in `run_blueprint`, not `place`, so the placement tests never spawn Python. **Don't gate it behind a marker file:** the handler command embeds absolute paths to `pythonw.exe` and `action.py`, so a Python upgrade or a repo move invalidates it — a marker is a cache that goes stale exactly when the truth changes, and re-registering every launch is what self-heals it. Registered as `$CLAUDE_CONFIG_DIR/hooks/speak.py` — **never a path to a checkout**, which is the whole point: that coupling silences every env at once when one directory moves. `sync_voice_hooks` self-heals registration into an already-placed env (register-only — there is no deregister branch, since no env is ever made silent by placement), replacing a hand-wired absolute-path group rather than adding beside it, and `ensure_tldr_instruction` appends the TL;DR section to the persona (append-only — the hook speaks that line and nothing else, so a persona that never writes one is silent). The scripts' state (voice pool, per-session leases, mutes) is **machine-wide**, not per-env: `%LOCALAPPDATA%\revoiced` / `~/Library/Application Support/revoiced` / `$XDG_DATA_HOME/revoiced`. That's what makes concurrent envs lease different voices and queue behind one playback lock. `voice.rs` (`aello voice mute|unmute|stop|status`) writes that shared state directly — no Python, no placed env, works from any directory — preserving unknown keys since the hook owns the rest of the file.

**Git attribution** — with `github`, `launch.rs` sets `GIT_AUTHOR_*`/`GIT_COMMITTER_*` to `<blueprint> <blueprint@aello.local>`, and the `/sync` github section appends an `Env: <blueprint>` commit trailer. Multi-blueprint repos stay traceable via `git blame` / `git log --author`.

## Seeded skills are the user's to run, not the agent's

Every seeded skill is manual-only twice over. `disable-model-invocation: true` in the frontmatter blocks the Skill-tool path. `templates::manual_only` adds a banner under the H1 blocking the other one: an agent that opens the `SKILL.md` with `Read` and works through the steps has *run the skill*, whatever route it took. That happened on 2026-08-03 — a `/sync` was carried out by hand, unasked, and reported as if the command had run, which is worse than not doing it at all because the user believes a checkpoint exists. The banner is not decoration: the frontmatter flag was already set and did not prevent it. `every_generated_skill_is_marked_user_only` asserts both halves on all four. A skill pinned with `.aello-keep` never regenerates, so its banner has to be added by hand (AlgoMainDev's `/sync` is the only such skill on this machine).

## The four response rules ride on a per-turn hook, not the persona

`src/hooks_user_prompt_submit.py` is bundled and registered on every placement, injecting four rules on **every prompt**: be concise, don't be sycophantic, never hand over a plan, and close with one block — the `TL;DR:` line with 3–4 numbered next steps beneath it. ~300 tokens per turn.

**Steps and TL;DR are one rule, not two.** They shipped as separate rules and lasted about an hour: the summary said a thing, the steps repeated it, and the reader had to reconcile two closing sections. Merged, the spoken line introduces the list it sits on top of. The TL;DR grew to two-to-four sentences to absorb what the steps used to duplicate. **Ordering is constrained by `speak.py`, not taste:** `extract_tldr` matches `^…TL;DR:\s*(.+?)$` and takes the last match, so the line must stay on ONE line — a wrapped summary is spoken with its tail cut off, silently — while numbered steps beneath match nothing and are safe. Verified by running a sample through the real `extract_tldr`.

**The next-steps rule has two halves and only one of them survived the first draft.** Steps that *stand alone* are the point — the user skips the prose and acts on `1, 2, 3, 4` — and the first wording got correct steps sitting under an essay that still had to be read to make sense of them, which is exactly what it was written to prevent. So the rule now states the assumption outright ("assume the user skips every word above them", no step saying "as described above") **and** the concise rule caps the prose ("a few sentences — if something matters it goes in a step, not a paragraph"). They only work as a pair; loosen either and the wall of text comes back with a numbered list stapled to it.

**It also reads as the opposite of the no-plans rule if the wording is careless.** The line between them is whose hands the actions are in: a plan is what *the agent* is about to do, held for sign-off; the steps are what *the user* does next. The no-plans rule therefore no longer says "no numbered proposals" (it now says don't lay out what you intend to do and wait for sign-off), and the steps rule says "their actions, not yours" in as many words. The order on the page is fixed and stated in the rule: prose, then the `TL;DR:` line, then the steps beneath it, and nothing after those.

**The no-plans rule is enforced twice**, like the seeded skills are. `src/hooks_pre_tool_use.py` is a bundled `PreToolUse` hook matching `EnterPlanMode|ExitPlanMode` (`PLAN_TOOLS`) that denies both, so plan mode is unavailable and not merely discouraged; the injected text is what catches the other route, a proposal written as ordinary prose, which is what a plan usually looks like. The **matcher** is load-bearing and is asserted by a test: an unmatched `PreToolUse` group fires on every tool call, which on Windows is a process spawn per `Read` in every env. `ensure_own_hook` gained `ensure_own_hook_matching` for exactly this. **What is measured and what is not:** a `PreToolUse` deny does block a tool and hand its `permissionDecisionReason` back (2026-08-03, against `Read` — it returned the reason instead of the file), and the matcher does scope it (a `Glob` in the same run never reached the hook). Whether the plan tools emit a `PreToolUse` event at all is **unverified** — `claude -p` never calls `ExitPlanMode` under `--permission-mode plan` across three attempts, so print mode cannot answer it and the check needs one interactive session. A denial appends to `<env>/hooks/plan-blocked.log`; nothing reads it, and it exists solely so the first real denial settles what the tests could not. An empty log everywhere means the block never fires and the text is carrying the rule alone — which is the guard-that-never-fired shape this repo keeps hitting, so check it rather than assuming.

**Why per turn.** All four govern how a single response is written, and style decays — an instruction delivered once at session start is buried by turn eighty, which is when padding and reflexive agreement return. **Why not the persona.** It is written once and never clobbered, so an edit there reaches *no* existing env; `place()` rewrites this script every run, so a wording change reaches all of them on their next launch. It is also the file most likely to be rewritten wholesale — `/regenerate-claude-md` exists to do exactly that — which is a poor home for the voice's only input.

Started as a hand-registered experiment in TechnicalDirector on 2026-08-03; bundled on the same day once the user asked for conciseness and anti-sycophancy fleet-wide, since this was already the only channel that self-propagates. `ensure_own_hook(settings, "UserPromptSubmit", "user-prompt-submit.py")` heals it into existing envs, and it runs **before** `ensure_tldr_instruction` so an adopting env stops getting the persona append on the same placement rather than one run later.

`ensure_tldr_instruction` + `injects_tldr_per_turn` survive as a **fallback**: unregister the hook by hand and the persona append returns, so the voice can't go silent for want of an instruction. The 40 envs placed before this carry the TL;DR section in their personas already and will now also get it per turn — duplicated, harmless, and not worth editing a user-owned file to fix. Enforcement never really lived in either place: `speak.py` exits 2 on a response with no TL;DR line and asks for one, so the instruction only ever saved a round trip.

`user_prompt_submit_hook_carries_the_five_response_rules` pins the wording, because the injected text *is* the product here — a dropped rule would be invisible.

## Seeded skills are regenerated — `.aello-keep` opts out

All four seeded skills are written **unconditionally on every `place`** (no existence check), which is what makes a role change reach an env placed months ago. The cost: a skill hand-edited for one project was silently restored to the generated version on the next run, and — worse — the github `/sync` step then mirrored that generated version over the custom one in `claude-internal/`, committing it. The edit survived only in git history, nowhere anyone would look.

`<env>/skills/<skill>/.aello-keep` (empty file) pins one skill: `place` neither regenerates nor removes it. The removal branch matters — a hand-written `/sync` isn't stale just because the blueprint became standalone, so a kept skill skips `remove_file` too. `skill_kept` + `seed_skill` in `project.rs`; the marker lives beside the skill rather than in `config.toml` so it travels with the env dir and is visible where the editing happens. A kept skill no longer tracks its role — that's the trade, and deleting the marker restores the generated version.

## `/sync`

Generated per blueprint from its role's capability expansion (`templates::render_sync_skill`), seeded to `<env>/skills/sync/SKILL.md` when `caps.any()` — i.e. everything but `standalone`. Manual-only (`disable-model-invocation: true`) — replaces the old auto-commit hooks. A `standalone` blueprint gets no skill at all; a `contributor` gets git + `CHANGELOG.md` and no README/docs/project-CLAUDE.md sections. Sections, in order: repo health (github), reconcile **memory first** then the enabled docs (two-way), mirror env config into `claude-internal/<name>/` + stage by path (github), commit + rebase-before-push with `Env:` trailer (github).

The staging rule ("only what you created or modified this session") has one carve-out that has to stay explicit: `*.HANDOFF.md` and `*.NOTE.md` are created *during* the session and deleted on the next boot, so the rule as literally written told you to commit them. In a repo aello scaffolds they are **not** gitignored — the `github` role seeds only the `.claude-env-*` line — so nothing else stops it, which is why the carve-out has to be in the skill text rather than left to `.gitignore`. (aello's *own* repo does ignore `*.HANDOFF.md` and `*.NOTE.md`, added by hand in `dec3fd9`. That is belt-and-braces here and says nothing about the repos the skill is generated into — don't drop the carve-out on the strength of it.)

## `/handoff`

Universal counterpart to `/sync` (`templates::render_handoff_skill`), seeded **unconditionally** for every blueprint at `<env>/skills/handoff/SKILL.md` (no role gate — even a standalone blueprint gets it). Manual-only (`disable-model-invocation: true`), tools `Write, Read, Bash`. At session end it writes a transient, untracked `<name>.HANDOFF.md` at the project root so the next session resumes after a full `/clear` (not a compact — a clear leaves no summary, so the note is fully self-contained: read-first pointers, what shipped + commit shas, open threads/next steps, gotchas). The filename is **prefixed with the blueprint name** so co-located blueprints in one repo don't clobber each other's handoff; the SessionEnd hook reads the same `<name>.HANDOFF.md` (it derives the name from `CLAUDE_CONFIG_DIR`). Read on boot, then deleted.

## `/note`

Universal too (`templates::render_note_skill`), seeded **unconditionally** for every blueprint at `<env>/skills/note/SKILL.md` alongside `/handoff`. Manual-only (`disable-model-invocation: true`), tools `Write, Read, Bash`. **The target need not share this repo** — the skill resolves the target's project root and writes there, because the SessionStart hook only reads its *own* project root, so a cross-repo note left here is a dead letter that looks delivered. It originally assumed one shared repo and reported a target it couldn't find here as a typo; that misdiagnosed the common multi-repo case twice on 2026-08-02. Casing must be the blueprint's canonical form (the hook matches `<Name>.NOTE.md` exactly — wrong case is silent on a case-sensitive filesystem). Distinct from `/handoff`: `/handoff` is a note to *self* for the next session, `/note <target>` leaves a note **for another environment** — the common multi-blueprint case where one env touches something the other owns, or hits a problem on its side. Invoked with the target blueprint name as the argument (`/note frontend`); the note **overwrites** `<target>.NOTE.md` at the project root (the target env's inbox) with a single current note — the target reads it immediately and deletes it, so only the latest matters. Heading `from <name>` attributes the authoring blueprint; sections: what I was doing / the problem / what you need to fix.

## `/twosentences`

Also universal (`templates::render_twosentences_skill`), seeded **unconditionally** for every blueprint at `<env>/skills/twosentences/SKILL.md` alongside `/handoff`. Manual-only (`disable-model-invocation: true`), no tools (empty `allowed-tools` — it's a pure text task). Condenses the previous assistant response into exactly two sentences, output with no other text.

## Development rules

- **Every user-facing change gets a `CHANGELOG.md` entry**, in the same commit as the code.
- **Small, scoped commits** — one change per commit; don't bundle unrelated edits.
- **Verify**: `cargo build --release` + `cargo test` must be green before pushing. Add a test for new behavior (templates/place/launch logic is all unit-testable without launching Claude).
- **Simplicity & surgical edits** — minimum code; match surrounding style; touch only what's required.

## Release process

Push to `main` → GitHub Actions:
1. **bump** job resolves the version to release: if `Cargo.toml`'s version **already has a `vX.Y.Z` tag** it increments the patch (+0.0.1), commits `release: vX.Y.Z [skip ci]` and pushes via `GITHUB_TOKEN` (does not re-trigger CI); if it does **not**, a human set it by hand and it ships **exactly as written**, with no bump commit. That second branch is why `v0.2.0` exists — a patch bump can only ever produce X.Y.(Z+1), so a deliberate minor bump used to come out as 0.2.1 and the intended version never existed. Needs `fetch-depth: 0` + `fetch-tags: true` at checkout, or every version looks unreleased and the same one is republished forever.
2. **build** jobs (ref: the bump commit sha, so the binary reports the new version) build four targets: `x86_64-unknown-linux-gnu` → `aello-x86_64-linux`, `x86_64-pc-windows-msvc` → `aello-x86_64-windows.exe`, `aarch64-apple-darwin` → `aello-aarch64-macos`, `x86_64-apple-darwin` → `aello-x86_64-macos` (the Intel Mac build cross-compiles on the Apple Silicon runner). All are **unsigned** — no Apple Developer account, no Windows cert; `install.sh` clears the macOS quarantine xattr and the README documents SmartScreen. The asset↔platform map is duplicated in `update.rs` and `install.sh`; change all three together.
3. **publish** generates `SHA256SUMS` (`sha256sum aello-*`) and uploads the binaries + `SHA256SUMS` to **two** releases: the immutable **`vX.Y.Z`** tag (created at the bump commit, flagged `--latest`) and the permanent rolling **`latest`** tag (`--clobber`, explicitly `--latest=false`). `aello update` hits `/releases/latest` → resolves to the versioned release; `install.sh` and old binaries hard-code the `latest` tag's download URL, which is why both are published. `aello update` verifies the downloaded binary against `SHA256SUMS` before installing (verify-if-present, so releases predating the manifest still update), so keep publishing it. Never delete+recreate a release (a draft state breaks `aello update` with a 404).

Release notes must **end with the build sha** — `aello update` reads the commit from the last whitespace token of the body. After CI, `git pull --rebase` to sync the bumped `Cargo.toml` before the next local `cargo install`. Minor/major versions are bumped manually in `Cargo.toml`. If a plain push doesn't trigger the workflow, `gh workflow run release.yml --ref main` is the fallback.

## Build & install

```sh
cargo build --release          # writes to target/ — safe while aello is running
cargo test                     # unit tests, no Claude launch needed
cargo install --path . --force # replace ~/.cargo/bin/aello with the local build
```
