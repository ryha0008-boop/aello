Decisions you can't recover from code — do NOT redo these:
- **Auth = long-lived non-rotating CLAUDE_CODE_OAUTH_TOKEN** via `aello login`/`claude setup-token`, NOT copying `.credentials.json`. Cred-copy was tried + abandoned: OAuth refresh tokens rotate (single-use), so concurrent envs invalidate each other. The user runs MANY blueprints concurrently — this is the reason.
- **Onboarding gotcha:** token authenticates the API but interactive claude shows its first-run wizard on a fresh config dir. `mark_onboarded` seeds `hasCompletedOnboarding:true` into `.claude.json` so it skips it. (That wizard WAS the "still asking for login" bug.)
- **`aello login` tees `claude setup-token` stdout** so the auth URL is visible on a headless VPS (a plain pipe swallows it → looks hung).
- **/sync replaces auto-hooks:** helo's Stop/UserPromptSubmit auto-commit-every-turn hooks were flaky/naggy and removed. /sync is MANUAL (`disable-model-invocation:true`). Only PostCompact hook survives (transcript saver, proven reliable). Don't reintroduce enforcement hooks.
- **/sync is GENERATED per blueprint** (`templates::render_sync_skill(caps,name)`), not static variants — contains only sections for enabled caps; no-github blueprint gets zero git talk + no Bash tool.
- **Per-env git attribution** (the core multi-agent point): with `github`, launch.rs sets GIT_AUTHOR_* AND GIT_COMMITTER_* = `<blueprint> <blueprint@aello.local>`, plus an `Env:<blueprint>` commit trailer — so git blame / log --author reveal which blueprint did what.
- **Two CLAUDE.md layers:** global persona = env CLAUDE.md (set once); project = repo CLAUDE.md (--project-md). Memory is separate/automatic. [[aello-overview]]
- **Partial capabilities are the multi-agent design, not leftover config — do not "simplify" them away.** The user recalled the rationale 2026-08-03 and the data confirms it exactly: a repo worked by several blueprints has **one maintainer** holding all five caps, and **contributors** holding `github` (± `changelog`) who commit their code but never touch `CLAUDE.md`, `docs/` or the README. shelly = ShellyCore (all five) + ShellyFrontEndDev (github, changelog); cleaning-website = CleaningCompanyMainDev (all five) + Cleaning3DDev + CleaningBackendDev (github only); desktop-automation and env-runner follow the same shape with the secondaries on none. **The analysis trap:** counted fleet-wide, 35/39 blueprints look all-or-nothing and the granularity looks pointless — that reading is an artifact of the wrong unit. Group **by repo** and the second role is obvious. Whenever a per-blueprint setting looks unused, check it per project before concluding anything. **BUILT 2026-08-03, shipped in v0.2.0.** The five flags are now `Role` (`models.rs`): **maintainer** = all five, **contributor** = `github` + `changelog`, **standalone** = none. Contributor keeps the changelog (the user's call — it matches ShellyFrontEndDev exactly, so no blueprint changed behaviour, and it matches the "every user-facing change gets an entry in the same commit" rule). `Role::caps()` expands into the existing `Capabilities` struct, so `project.rs`/`templates.rs` were untouched — a role is only a restriction on which combinations are offered. `Config::migrate_roles` runs on **every** load (not behind a marker, so a restored backup heals itself) and `legacy_caps` is `skip_serializing`, so `[blueprints.caps]` vanishes on the next save. Verified against the real config: 39 caps blocks → 0, 29 maintainer / 3 contributor / 7 standalone. PersonallyDev (4 of 5) → maintainer, the user's call, so it now maintains a README it did not before.

- **Persona lifecycle: `coder` / `none` / `custom`, generation in a sidecar (2026-08-03, v0.2.8).** The user's design, and simpler than what was first proposed. A coding project starts on `coder`, anything outside IT on `none`, and both become `custom` the first time a generated persona is accepted — after which `templates::resolve` returns `None` and `place` writes nothing over `<env>/CLAUDE.md`. **Why explicit `none` instead of an absent key:** a blank persona should read as a decision, and that is what lets `custom` mean something. **Why `sysadmin` was deleted:** barely used and effectively coder with different nouns; its one blueprint migrated to `custom` rather than `coder`, because the env already holds the sysadmin text (personas are never clobbered) and `coder` would have claimed text that env does not have. **Why paths survive and are not in the picker:** five blueprints point at persona files the user maintains and EnvRunner2–4 *share* one file deliberately, so folding them into `custom` would freeze three copies and end the sharing silently. **Why the generation is a sidecar (`<env>/persona.gen`) and not a config key:** `Config` and the placed `.aello.toml` are both serialized from a struct and rewritten on every `place`, so anything written there by something else is dropped — the same mechanism that makes `[blueprints.caps]` vanish. Config answers *whether* an env has a custom persona; the sidecar answers *which generation*, next to the file it describes. It is also **per env, not per blueprint**, because `PersonallyDev` is placed in two projects with two different personas. **Why a command and not a skill writing files:** `aello persona <name> --from <file> --project <dir>` does all three writes together and keeps the config edit inside serde. `/regenerate-claude-md` proposes and installs nothing; `/regenerate-claude-md-accept` installs. The first now **must** read contextdb before judging eligibility — and must check whether the `SessionEnd` hook was even registered before reading a thin archive as a young project. **First real use, same day: TechnicalDirector accepted `gen1 2026-08-03`** off 21 archived sessions spanning 5½ weeks. What that run taught, beyond the mechanism working: the persona a generated one replaces is often *already* hand-shaped while the config still says `coder`, so "which envs have a real persona" was unanswerable before `custom` existed — that is the gap the state was added to close, and it was wider than assumed. A generated persona also now deliberately omits the TL;DR, conciseness and anti-sycophancy rules, because the per-turn hook delivers all three to every env and a persona copy costs context on every turn ([[aello-dev-gotchas]] #15). [[aello-dev-gotchas]] #16, #22

**Second accepted persona: CleaningCompanyMainDev `gen1 2026-08-03`** (`coder` → `custom`, 3957 → 3731 bytes). The first one derived from evidence rather than judgement: 41 archived sessions over 39 days, 37 transcripts still resolving on disk, **367 of the owner's own turns** mined out of them — so the rules trace to what was said, not to an agent's summary of it. What that surfaced, and what a persona review should look for next time: **half the outgoing file was actively wrong.** Its "hard guardrail" forbade touching `components/three/*`, `app/api/*` and migrations, but the owner retired the multi-env split on 2026-07-17 ("commit everything even other lanes changes"), and the measurement confirmed it — 52 commits by that env and **zero** by the other two since 2026-07-15, both dormant since mid-July. A persona goes stale silently because nothing ever fails; only the git log and contextdb say so. Two other findings worth carrying: the env's own review of the proposal reported five sentences "truncated mid-word" that were **intact in the file** (corruption in the paste relay, not the artefact — do not "fix" what you can still read whole), and it asked for the TL;DR section back, not knowing `injects_tldr_per_turn` already restores it automatically if the hook is unregistered — an agent's report about aello internals is the one thing it cannot verify. See [[aello-dev-gotchas]] #15, #16.

**Third accepted persona: ProjectifiableDev `gen1 2026-08-03`** (`coder` → `custom`, 1790 → 3857 bytes, off 36 archived sessions over 5 weeks and 112 of the owner's own turns). The outgoing file was the **stock `coder` template byte-for-byte** plus the TL;DR append — so unlike CleaningCompanyMainDev nothing was stale, there was simply nothing there. That is the more common case among the 24 blueprints still on `coder`, and it makes the gate in `/regenerate-claude-md` the load-bearing part: the question is not "is the persona wrong" but "has enough happened to write one". The reviewing env repeated the same class of error as the second run — it claimed `place()` would clobber an in-env persona on the next run and recommended routing to a **path** to avoid it, when `project.rs` writes the persona only `if !path.exists()` and `custom` is exactly the mechanism for a one-blueprint persona (paths exist for files *shared* across envs, which is why EnvRunner2–4 have one). Its own cited precedent, `Cleaning3DDev`, points at a path *inside* a gitignored env dir, contradicting the advice it was cited for. **Twice now the target env has been wrong about aello's own internals and right about its project** — take its editorial notes, verify its mechanism claims in the source. Its editorial notes here were good and all were taken: a "pick one and say why" bullet that contradicted both the per-turn hook and the env's own `working-style` memory, a redundant reproduce-before-fixing bullet, and war-story evidence that justified writing a rule but did not need re-reading every turn (74 → 62 lines). See [[aello-dev-gotchas]] #15, #16.
